# ADR-0001: 采用 React + TypeScript、FastAPI + Pydantic、SQLite 与 Transformer

日期：2026-10-14 | 状态：Accepted | 取代：无 | 被取代：无

## 背景

项目是对大学时期 Django 网上小卖铺课程设计的重做，目标是供老同学和技术面试展示。原商品数据库遗失，结账流程当年未能正确计算金额。本项目首版需支持约百种重建商品、浏览与购物车、结账创建模拟订单，以及后台商品/库存管理和订单查看；不接真实支付、不要求顾客登录，仅需本机运行。

人类已确认希望使用 React、FastAPI、Pydantic、SQL、Transformer 和 TypeScript，并选定 SQLite。开发者电脑已有 nvm 与 uv；项目所有组件放在同一仓库。

## 决策

- 前端采用 **React + TypeScript**。
- 后端采用 **FastAPI + Pydantic**。
- 关系型 SQL 数据库采用 **SQLite**。
- 结账计算使用 **训练后的 Transformer 模型**；设计意图为将乘法展开为加法并归并调用模型。具体模型结构、调用契约与训练/推理实现以人类后续提供的模型设计文档为准，不由本 ADR 臆定。
- 前后端、数据库与模型相关项目文件共同置于一个仓库；首版在本机运行，不要求部署。

## 考虑过的方案

- 沿用 Django 课程设计的技术栈。
- 采用 FastAPI + Pydantic 作为 API 服务，配合 React + TypeScript 前端。
- SQL 数据库采用 PostgreSQL 或 SQLite。
- 结账计算采用 Transformer，遵从人类指定的项目目标；传统计算器仅可作为测试对照或经规格批准的辅助方案，不擅自替换目标模型。

## 理由

- React + TypeScript、FastAPI + Pydantic 与原课程设计技术栈不同，适合作为本次全栈重做和工程实践展示的基础。
- SQLite 不要求额外安装或运行数据库服务；数据规模小且项目只需本机演示，符合人类选择和首版运行范围。
- Pydantic 可为 API 边界提供显式运行时数据验证。
- Transformer 是项目明确的炫技/学习目标，需要进入真实结账计算流程；其准确语义必须在收到设计文档后通过规格与测试固化。

## 后果

- 好处：技术栈符合人类确认的目标；依赖服务少、本机启动成本低；前后端和模型相关工作可以在一个仓库中统一验证。
- 代价与风险：SQLite 的并发写入能力及多用户部署能力有限；若目标转为线上或高并发服务，需要重新评估数据库与部署方式。Transformer 进行精确金额运算具有非传统复杂度，必须先明确精度和失败边界，并以规格测试验证。
- 尚未由本 ADR 决定：前端组件库与包管理器、SQL 访问库/ORM、数据库迁移工具、Python 类型检查/lint 工具、Transformer 框架、训练实现与训练硬件；这些需在对应任务/设计输入明确后选择。

## 触发重新评估的条件

- 项目从本机演示转向线上生产、多实例部署或明显提高并发写入需求。
- SQLite 事务、并发或运维限制阻碍已确认的业务目标。
- 后续模型设计文档证明 Transformer 方案不能满足明确的结账准确性/精度验收，需由人类重新裁决。
- 人类明确改变技术栈或首版部署边界。
