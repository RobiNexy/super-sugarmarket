# ADR-0006: 无认证的房间号结账，以待送货订单占用可售库存

日期：2026-10-16 | 状态：Accepted（人类确认，见 Q-012）| 取代：无 | 被取代：无

## 背景

Sugarmarket 是酒店楼下的小卖铺，顾客当面付款、老板送货上门。系统不需要账户体系。结账需要解决两个问题：订单归属，以及下单后库存的占用。

Q-002 规定库存在老板完成订单时扣减。若只按 `stock_quantity` 判断下单，两笔待送货订单可能同时占用同一件库存，导致超卖。

## 决策

- 身份：顾客以房间号标识订单，无密码、无登录。后台同样无认证（Q-003）。
- 购物车：只存于浏览器 localStorage，服务端不保存购物车。
- 库存：下单时不扣减 `stock_quantity`。可售库存 = `stock_quantity` − 待送货订单占用量（下限 0）。结账在 `BEGIN IMMEDIATE` 事务内按可售库存截断数量。
- 扣减时点：老板完成订单时扣减，与 Q-002 一致。
- 金额：数据库以分存储；接口与前端以元字符串传输；前端不做金额运算。
- 结账金额：由 Transformer 经 `tree_sum` 计算；精确加法仅用于档位诊断（Q-005、Q-008、Q-011）。

## 考虑过的方案

- 下单时直接扣减库存：实现简单，但取消或退货需要回补，且与 Q-002 冲突。
- 购物车存服务端并预占库存：需要会话，超出“只需把订单塞进数据库”的范围。
- 完全不校验库存：会出现超卖，与“有多少结多少”的规则冲突。

## 理由

- 占用量由待送货订单即时计算，无需额外库存表，与 SQLite 单文件部署一致。
- 同一事务内计算与写入，避免两笔订单并发占用同一库存。
- 与 Q-002 的扣减时点保持一致。

## 后果

- 好处：无需认证与会话；库存语义清晰；订单即真相来源。
- 代价与风险：若老板直接调低 `stock_quantity` 至低于占用量，可售库存显示为 0，完成订单时可能因库存不足被拒绝（需补货）。
- 风险：SQLite 写锁在高并发下会排队；本机演示可接受。

## 触发重新评估的条件

- 需要支持多个店员或远程下单。
- 需要取消或退货并自动回补库存。
- 订单量增长到 SQLite 写锁成为瓶颈。
